# AeroRAG-X Observability and Reliability

This document describes the production-observability layer implemented in Phase 13 of AeroRAG-X.

The goal is to make the serving path measurable and diagnosable without placing raw user queries, retrieved evidence, answer text, API keys, authorization headers, or provider secrets into logs, metrics, or trace attributes.

## Implemented observability stack

AeroRAG-X now provides:

- structured JSON application logs;
- per-request `X-Request-ID` correlation;
- provider request-ID correlation when a remote provider is called;
- runtime startup timing;
- HTTP request timing;
- end-to-end RAG stage timing;
- detailed retrieval, facet, and reranker timing;
- Prometheus metrics through `GET /metrics`;
- deterministic HTTP load validation;
- OpenTelemetry HTTP and application tracing;
- OTLP/HTTP trace export;
- local OpenTelemetry Collector validation.

The public query response schema is unchanged by observability instrumentation.

## Observability flow

```text
HTTP POST /v1/query
        |
        v
FastAPI SERVER span
        |
        v
aeroragx.query
        |
        +--> aeroragx.retrieval
        |       |
        |       +--> aeroragx.reranker
        |               |
        |               +--> aeroragx.hybrid_retrieval
        |                       |
        |                       +--> aeroragx.bm25
        |                       +--> aeroragx.dense
        |                       +--> aeroragx.hybrid_fusion
        |
        +--> aeroragx.evidence_build
        +--> aeroragx.sufficiency
        +--> aeroragx.provider
        +--> aeroragx.citation_resolution
```

Facet-aware retrieval may invoke the reranker/hybrid stack more than once for a single user query. The resulting trace therefore exposes repeated retrieval work instead of collapsing it into one opaque latency number.

## Structured JSON logging

Primary implementation:

```text
src/aeroragx/observability/logging.py
```

Important events include:

```text
runtime_load_started
runtime_load_completed
runtime_load_failed
http_request_completed
http_request_failed
grounded_query_completed
```

The query-completion event includes operational metadata such as:

- request ID;
- trace ID and span ID when tracing is active;
- candidate/evidence depth;
- retrieval/reranker/facet timings;
- evidence-sufficiency result;
- provider call/bypass state;
- provider attempts and latency when available;
- token and estimated-cost telemetry when available;
- claim, citation, and source-document counts.

Raw query text and retrieved evidence text are deliberately excluded.

## Correlation identifiers

AeroRAG-X keeps three identifiers conceptually separate:

### AeroRAG-X request ID

Generated by the application for every HTTP request.

Returned as:

```text
X-Request-ID: <uuid>
```

Structured errors carry the same request ID in the JSON body.

### OpenTelemetry trace/span IDs

When tracing is active, structured logs may contain:

```text
trace_id
span_id
```

The `grounded_query_completed` event is correlated with the `aeroragx.query` span.

The `http_request_completed` event is correlated with the FastAPI server span.

### Provider request ID

When an external provider supplies a provider-side request identifier, AeroRAG-X stores it in provider telemetry.

It is not treated as the same identifier as the AeroRAG-X request ID.

## RAG timing telemetry

End-to-end RAG timing is internal metadata and is not added to the public HTTP response schema.

Tracked stages include:

```text
retrieval_ms
evidence_build_ms
sufficiency_ms
provider_stage_ms
citation_resolution_ms
total_ms
```

Detailed retrieval telemetry includes:

```text
bm25_ms
dense_ms
hybrid_fusion_ms
reranker_scoring_ms
retrieval_search_count
facet_search_count
facet_overhead_ms
facet_used
```

These timings make it possible to distinguish retrieval overhead, dense search, cross-encoder scoring, facet expansion, provider latency, and citation-resolution work.


The endpoint is excluded from the public OpenAPI schema.

Representative counters:

```text
aeroragx_http_requests_total
aeroragx_query_requests_total
aeroragx_query_success_total
aeroragx_query_errors_total
aeroragx_insufficient_evidence_total
aeroragx_provider_calls_total
aeroragx_provider_bypasses_total
aeroragx_provider_errors_total
```

Representative histograms:

```text
aeroragx_http_request_duration_seconds
aeroragx_rag_duration_seconds
aeroragx_retrieval_duration_seconds
aeroragx_reranker_duration_seconds
aeroragx_provider_duration_seconds
```

Metric labels intentionally avoid request IDs, queries, document IDs, chunk IDs, and other high-cardinality identifiers.

## Deterministic local load validation

Phase 13 used the reusable harness:

```text
scripts/load_test.py
src/aeroragx/observability/load_test.py
```

The validation used deterministic local generation with:

```text
AERORAGX_RUNTIME_MODE=local
AERORAGX_CANDIDATE_TOP_K=20
AERORAGX_EVIDENCE_TOP_K=5
OPENAI_API_KEY unset
```

Measured results:

| Run | Measured requests | Concurrency | P50 | P95 | P99 | Throughput | Failures |
|---|---:|---:|---:|---:|---:|---:|---:|
| Smoke | 5 | 1 | 398.668 ms | 412.840 ms | 413.926 ms | 2.491 req/s | 0 |
| Baseline | 20 | 2 | 587.053 ms | 626.902 ms | 630.722 ms | 3.383 req/s | 0 |
| Stress | 20 | 4 | 993.928 ms | 1117.138 ms | 1126.538 ms | 3.966 req/s | 0 |

The cumulative validation produced:

```text
query_requests_total = 50
query_success_total = 50
query_errors_total = 0
provider_calls_total{provider="fake"} = 50
```

Interpretation:

- no request failed through concurrency 4;
- throughput increased with concurrency;
- latency increased more quickly between concurrency 2 and 4;
- the local CPU retrieval/reranking path therefore begins to show contention before reliability degrades.

These measurements are a local engineering baseline, not a production SLA. The concurrency-1 result is a five-request smoke run and is not an equal-size throughput comparison with the 20-request concurrency-2 and concurrency-4 runs.

## OpenTelemetry configuration

Primary implementation:

```text
src/aeroragx/observability/tracing.py
```

Tracing is disabled by default.

Environment variables:

```text
AERORAGX_OTEL_ENABLED
AERORAGX_OTEL_ENDPOINT
AERORAGX_OTEL_SERVICE_NAME
AERORAGX_OTEL_SERVICE_VERSION
AERORAGX_OTEL_ENVIRONMENT
AERORAGX_OTEL_SAMPLE_RATIO
```

Default endpoint:

```text
http://127.0.0.1:4318/v1/traces
```

Example:

```bash
export AERORAGX_OTEL_ENABLED=true
export AERORAGX_OTEL_ENDPOINT=http://127.0.0.1:4318/v1/traces
export AERORAGX_OTEL_SERVICE_NAME=aeroragx
export AERORAGX_OTEL_SERVICE_VERSION=0.1.0
export AERORAGX_OTEL_ENVIRONMENT=local
export AERORAGX_OTEL_SAMPLE_RATIO=1.0
```

Sampling is parent-based with a trace-ID ratio sampler.

Operational endpoints are excluded from FastAPI tracing:

```text
/health
/ready
/metrics
```

## Local OpenTelemetry Collector

Collector configuration:

```text
configs/otel-collector.yaml
```

The local validation configuration accepts OTLP/HTTP on port `4318` and forwards traces to the Collector debug exporter.

Start:

```bash
docker run -d \
  --name aeroragx-otel-collector \
  -p 127.0.0.1:4318:4318 \
  -v "$PWD/configs/otel-collector.yaml:/etc/otelcol/config.yaml:ro" \
  otel/opentelemetry-collector
```

Inspect:

```bash
docker logs aeroragx-otel-collector 2>&1 | tail -50
```

Stop:

```bash
docker rm -f aeroragx-otel-collector
```

Phase 13 manual validation confirmed the OTLP HTTP receiver started successfully on port `4318`, the AeroRAG-X service started with tracing enabled, and a deterministic `/v1/query` request completed with correlated request, trace, and span IDs.

## Privacy and redaction policy

Do not place any of the following in logs, metric labels, or trace attributes:

```text
raw query text
raw evidence text
answer text
claim text
API keys
Authorization headers
Bearer tokens
provider credentials
```

Safe operational attributes include:

```text
request ID
trace/span IDs
model/provider names
top-k settings
counts
timings
success/failure state
facet-used flag
provider attempts
token counts
estimated cost
```

Provider and internal exception details remain hidden from API clients.

## Failure-mode runbook

### Port 8000 is already in use

Inspect first:

```bash
lsof -nP -iTCP:8000 -sTCP:LISTEN
```

Then inspect the identified PID:

```bash
ps -p <PID> -o pid,ppid,command
```

Stop only the confirmed process.

### Port 4318 is already in use

```bash
lsof -nP -iTCP:4318 -sTCP:LISTEN
```

Inspect the owning process/container before stopping anything.

### Runtime is not ready

Check:

```bash
curl -sS http://127.0.0.1:8000/ready
```

Then inspect the Uvicorn startup logs for `runtime_load_failed`.

Do not run load validation until readiness is true.

### OTLP export does not appear

Verify:

```bash
echo "$AERORAGX_OTEL_ENABLED"
echo "$AERORAGX_OTEL_ENDPOINT"
docker ps --filter name=aeroragx-otel-collector
docker logs aeroragx-otel-collector 2>&1 | tail -50
```

Confirm the endpoint includes `/v1/traces`.

### Metrics unexpectedly increase

Warmup requests count as real query requests.

Health, readiness, and metrics probes affect HTTP metrics but do not increment grounded-query counters.

### Provider telemetry is null

This is expected when the evidence-sufficiency layer bypasses the generation provider.

## Phase 13 outcome

Phase 13 adds production-oriented visibility around the existing grounded RAG behavior without changing the trust boundary:

- retrieved evidence remains untrusted input;
- provider output remains non-authoritative for citations;
- evidence insufficiency still fails closed;
- logging/tracing does not expose raw query/evidence content;
- metrics avoid high-cardinality identifiers;
- the same shared runtime remains usable from CLI, evaluation, native FastAPI, and Docker.

The next project milestone is cloud deployment and production hosting.
